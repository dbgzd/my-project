\chapter{舆情分析系统需求与设计}
\label{ch:system_design}

本章从需求分析、总体架构、功能模块设计、数据库模式与接口规范、部署与运维设计等角度，系统性描述面向电商评论舆情分析的系统工程实现方案。内容兼顾功能性需求与非功能性约束，注重可复现性、可扩展性与运维可观测性。

\section{系统需求分析}
\label{sec:requirements}

本系统目标在于对电商评论进行高质量的主题抽取与情感分析，并支持按商品、类目和时间维度的可视化分析与告警。需求可分为功能性需求与非功能性需求。

功能性需求：

- 数据采集：支持从多平台（API、网页）定时或实时采集评论与元数据；支持断点续抓与增量抓取。 
- 数据预处理：包括清洗、分句分词、去重、语言检测与必要的文本扩展（短文本聚合）。
- 主题建模：支持批量主题训练及在线主题更新，并导出主题关键词与主题-文档分布。
- 情感分析：支持句子级与文档级情感判定、方面级情感抽取与情感强度评分。
- 融合分析与报表：按主题生成情感统计、支持时间序列分析、关键词云与可交互仪表盘。
- 告警与导出：对异常情感波动或关键话题触发告警，并支持数据导出（CSV/JSON）。

非功能性需求：

- 可扩展性：系统应支持水平扩展以应对数据量增长（如分布式爬取、批处理与流式处理扩展）。
- 可用性与容错：核心服务应支持高可用部署与容灾策略，保证在节点故障下不丢失采集任务与推理请求。 
- 性能：满足近实时分析的延迟目标（如新增数据在数分钟内完成情感分析与入库）。
- 安全与合规：遵循数据隐私与平台使用规范，保护用户隐私信息并支持访问控制与审计。 
- 可维护性：提供完善的日志、指标和可视化监控以支持运维与模型性能监控。

\section{系统总体架构}
\label{sec:architecture}

系统采用分层架构，主要包括数据采集层、数据处理与存储层、模型服务层、应用与展示层，以及运维监控层。图示（略）说明模块边界与数据流向：

- 数据采集层（Crawl \& Ingest）：负责异构数据采集、去重、队列化与原始数据持久化。
- 数据处理与存储层（ETL \& Storage）：负责数据清洗、分句分词、语言检测、向量化、以及关系型与检索型存储（如 MySQL + Elasticsearch）。
- 模型服务层（Topic \& Sentiment）：承担主题建模的离线训练与在线推理、情感微调模型的批量与在线推理服务，支持模型版本管理与 A/B 测试。 
- 应用与展示层（API \& UI）：提供 REST/gRPC 接口供前端或外部系统调用，提供仪表盘、报表与告警功能。 
- 运维监控层（Observability）：收集服务指标、日志与模型指标，支持告警与异常检测。

该架构支持独立扩展各层能力，并通过消息队列（Kafka/RabbitMQ）解耦采集与处理流程，使用容器化与编排（Docker + Kubernetes）实现弹性伸缩。

\section{功能模块设计}
\label{sec:modules}

本节详细说明各功能模块的内部职责、输入/输出与关键实现要点。

1) 数据采集模块（Collector）

- 职责：从多个数据源（平台 API、网页）采集评论与元数据，支持策略化调度与并发控制。
- 输入/输出：输入为爬取任务配置，输出为标准化的原始记录写入消息队列与原始存储。 
- 关键实现：代理池管理、重试与异常记录、断点续抓、抓取速率与合规策略。 

2) 数据预处理模块（Preprocessor）

- 职责：对原始文本进行清洗、分句、分词、去重与语言检测，生成用于建模的字段与特征。 
- 输入/输出：输入为原始记录，输出为清洗后的文本、词表、向量特征及元数据。 
- 关键实现：统一编码、正则/字典规则与 NLP 模型结合的文本清洗流水线、短文本聚合策略、并行化处理以提高吞吐。 

3) 存储与索引模块（Storage）

- 职责：提供事务型与检索型存储，支持 OLAP 风格统计与全文检索。 
- 典型设计：MySQL 保存业务元表，Elasticsearch/Opensearch 保存全文索引与聚合视图，冷数据归档到对象存储（S3 兼容）。 

4) 模型服务模块（Model Service）

- 职责：封装主题模型与情感模型的训练与推理接口，管理模型版本与配置。 
- 输入/输出：输入为清洗后文本或向量；输出为主题分布、主题关键词、情感极性与置信度。 
- 关键实现：离线训练任务调度（用作定期重训练）、在线批量与流式推理、微调流水线（QLoRA）、模型监控（精度、漂移）。

5) 融合与分析模块（Fusion \& Analytics）

- 职责：将主题分布与情感输出按规则或学习的方法融合，生成主题级情感统计、时间序列与告警判据。 
- 实现要点：定义一致性损失以指导融合训练，提供按主题聚合的指标与可解释性信息（高贡献词、示例句）。

6) 展示与告警模块（UI \& Alerting）

- 职责：为用户提供交互式仪表盘、查询与导出功能；对异常模式触发告警并支持规则配置。 
- 关键实现：可视化组件（趋势图、词云、分布图）、告警规则引擎、权限与审计日志。 

\section{数据库设计}
\label{sec:database}

数据库设计应兼顾分析性能与数据一致性，推荐采用多存储协同的设计。下面列出若干核心表的建议结构：

\begin{itemize}
	\item \texttt{raw\_comments}（原始评论表）：\\
		id (PK), source, source\_id, raw\_text, capture\_time, meta (JSON)
	\item \texttt{clean\_comments}（清洗后评论）：\\
		id (PK), raw\_id (FK), clean\_text, language, tokens, length, agg\_id（短文本聚合 ID）
	\item \texttt{comment\_features}（特征表）：\\
		id (PK), clean\_id (FK), embedding (向量), tfidf (JSON)
	\item \texttt{topic\_model\_versions}（主题模型元信息）：\\
		model\_id, version, train\_time, parameters (JSON), topic\_count
	\item \texttt{comment\_topics}（文档-主题分布）：\\
		clean\_id (FK), model\_id (FK), topic\_distribution (JSON)
	\item \texttt{sentiment\_results}（情感分析结果）：\\
		clean\_id (FK), model\_id, polarity, score, explain (JSON)
\end{itemize}

在 ER 图中，\texttt{raw\_comments} 与 \texttt{clean\_comments} 为一对一关系，\texttt{clean\_comments} 与 \texttt{comment\_topics}/\texttt{sentiment\_results} 为一对多（不同模型版本）。Elasticsearch 保留 \texttt{clean\_text} 的倒排索引与用于聚合查询的字段副本。

\section{接口与部署设计}
\label{sec:api_deploy}

接口规范：系统对外提供 RESTful API 与内部消息队列接口。示例 REST 接口包括：

\begin{itemize}
\item \texttt{POST /api/v1/comments/ingest}：接收批量或单条的原始评论数据，返回接收状态与任务 ID。
\item \texttt{GET /api/v1/comments/{id}}：查询清洗与分析结果（包括主题分布与情感结果）。
\item \texttt{GET /api/v1/topics/{model\_id}}：获取主题关键词与模型元信息。
\item \texttt{POST /api/v1/query}：基于时间、主题或关键词进行聚合查询并返回可视化所需的数据结构。
\end{itemize}

消息队列契约（示例）：

\begin{itemize}
\item \texttt{topic:raw\_comments}：生产者为采集模块，消费者为预处理模块；消息包含 \texttt{raw\_id} 与原始字段。 
\item \texttt{topic:clean\_comments}：生产者为预处理模块，消费者为模型服务与索引服务。
\end{itemize}

部署方案：

- 容器化：所有服务采用 Docker 容器打包；使用 Kubernetes 进行编排以实现自动扩缩与滚动升级。 
- 模型部署：使用模型服务器（如 TorchServe 或 Triton）或基于 FastAPI 的自定义推理服务，结合 GPU 节点池进行弹性伸缩。 
- 持续集成与交付（CI/CD）：采用 GitHub Actions / GitLab CI 构建镜像、运行单元测试与自动化部署。 
- 配置与秘密管理：使用 Kubernetes ConfigMap 与 Secret 管理配置与凭证，配合 Vault 等密钥管理器保证安全。 

运维与监控：

- 指标：服务层面的 Prometheus 指标（延迟、吞吐、错误率）与模型层面的指标（置信度分布、输入分布统计）。
- 日志：集中式日志（ELK / EFK）以支持审计与故障排查。 
- 模型绩效监控：定期在验证集上复跑关键指标，并对在线分布漂移触发告警。

\section{安全、合规与隐私}
为遵守数据隐私与平台规则，系统应执行敏感信息检测与脱敏流程；对外接口实施认证与授权（OAuth2 / JWT），并对敏感操作进行审计记录。对用户数据应制定保留策略并支持数据删除请求以满足合规要求。

\section{测试计划与验收标准}
系统测试应包括单元测试、集成测试、端到端测试与性能测试。验收标准建议包含：采集覆盖率、处理延迟满足 SLA、模型在指定验证集上达到基线指标（例如情感分类 F1 >= 0.75）、以及系统在负载下的稳定性指标。
